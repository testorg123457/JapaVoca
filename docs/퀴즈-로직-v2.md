## 0. 큰 그림

```
학습 트랙 결정 ─→ 항목 선택(SRS) ─→ 문제 생성(오답 3개 + 서명 토큰)
                                          │
                                          ▼
                                   클라가 답 제출
                                          │
                                          ▼
         토큰 검증 → 채점 → SRS 갱신 → QuizLog → Daily 집계
                                          │
                            ┌─────────────┴─────────────┐
                            ▼                           ▼
                     정답 시 캐시상자              당일 정답 10개마다
                     (등급·묶음 확률)              마일스톤 보너스
```

**두 가지 원칙이 전부를 지배한다.**

1. **정답 여부는 서버만 안다.** 정답 위치(`correct_index`)를 서명된 토큰에 넣어 발급하고,
   채점 때 그 토큰을 다시 검증한다. 클라가 보낸 "맞았다"는 절대 믿지 않는다.
2. **캐시는 자산이다.** 지급은 `rewards.services.earn()`만 통하고, 원장 기록 + 잔액 갱신이
   하나의 트랜잭션으로 처리된다(CLAUDE.md).

## 1. 학습 트랙 결정 — `resolve_study(user)`

`user.study_mode` 하나로 갈린다. 반환값은 `(item_type, subtype, level)`.

| study_mode | item_type | subtype | level | 콘텐츠 |
|---|---|---|---|---|
| `kanji` | `KANJI` | — | `user.study_level` | `Kanji` |
| `kanji_word` | `WORD` | `WordType.KANJI` | `user.study_level` | `Word` |
| `kana_word` | `WORD` | `WordType.KANA` | `user.study_level` | `Word` |
| `kana` | `KANA` | `Script.HIRA`/`KATA`/둘 다면 `None` | — | `Kana` |

- 가나 트랙은 히라·가타 토글(`study_kana_hiragana` / `study_kana_katakana`)로 스크립트를 정한다.
  둘 다 끄면 `NoContent`.
- `study_mode`가 `null`이면 온보딩 미완료 → `NoContent`.

## 2. 항목 선택 — `_pick_item_id()`

우선순위가 **딱 2단계**다.

1. **복습 기한이 지난 항목** — `SrsState.due_at <= now` 중 **`due_at`이 가장 이른 것**
   (= 가장 오래 밀린 것)부터.
2. **없으면 신규** — `SrsState`에 아직 없는 항목을 무작위(`order_by('?')`)로.
   가능하면 유저 급수와 같은 것을 우선.

필터:
- 트랙 범위 안에서만(`word_type` / `script`).
- 한자는 `jlpt_level`이 비어 있으면 제외(Word/Kana는 급수 데이터가 없어 미적용).
- `exclude_ids`로 **한 세트 안 중복 출제 방지**.

## 3. 문제 생성 — `_build_question_data()`

### 출제 방향

가나는 **글자→로마자 고정**이다(로마자→글자는 じ·ぢ 같은 동음 모호성 때문에 정답이 둘이 됨).
나머지 트랙은 매번 무작위로 방향을 정한다.

| question_type | 보여주는 것 | 고르는 것 |
|---|---|---|
| `word_to_meaning` | 표기(한자/단어/가나) | 뜻 |
| `meaning_to_word` | 뜻 | 표기 |

### 오답 3개 — `_distractor_texts()`

같은 종류에서 뽑되 **급수를 제한한다**. 전체에서 아무거나 뽑으면 난이도가 튀는 보기가 섞여
뜻을 몰라도 소거법으로 맞힐 수 있기 때문.

```python
DISTRACTOR_LEVELS = {
    'N5': ('N5', 'N4'),   # N5는 더 쉬운 급수가 없어 N4를 대신 씀
    'N4': ('N4', 'N5'),
    'N3': ('N3', 'N4'),
    'N2': ('N2', 'N3'),
    'N1': ('N1', 'N2'),
}
```

- 급수 풀에서 먼저 뽑고, **3개를 못 채우면 전체로 넓힌다**
  (오답이 모자라면 문제 자체가 버려지므로).
- 빈 값·정답과 같은 텍스트·중복은 걸러낸다.
- `Kana`는 급수 필드가 없어 항상 전체에서 뽑는다.

> ⚠️ **남은 구멍**: 오답이 트랙을 안 가린다. 가나단어 문제에 한자단어 오답이 섞일 수 있다.
> 뜻이 사실상 같은 동의어 오답도 못 거른다(정답이 둘이 되는 경우).

### 서명 토큰

정답 4개를 섞은 뒤 정답 위치를 `correct_index`로 기록하고, Django `signing`으로 서명한다.

```python
# 단발 토큰 (/quiz/next/) — TTL 300초
{'it': item_type, 'id': item_id, 'qt': question_type, 'ci': correct_index}

# 세트 토큰 (/quiz/set/) — TTL 없음, set_id 생존으로 검증
{..., 'sid': quiz_set_id, 'ord': order}
```

## 4. 세트 관리 — `build_quiz_set()`

메인 앱은 **10문제 세트**(`SET_SIZE = 10`) 단위로 푼다.

### 세트를 새로 만드는 조건

```
미완료 세트가 있나?
├─ 있음 → 리셋 경계 이전에 시작했나?
│         ├─ 예 → 폐기(abandoned_at)하고 새로 생성   ← 아래 참조
│         └─ 아니오 → 모든 문항이 answered인가?
│                     ├─ 예 → completed 처리 후 새로 생성
│                     └─ 아니오 → 그 세트를 이어서 반환
└─ 없음 → 쿨다운 확인 → 새로 생성
```

### 리셋 경계 — `SET_RESET_HOUR = 3`

세트는 **시작 시점에 10문제를 미리 뽑아 저장**한다. 하루가 지나면 SRS 기한이 다 바뀌어
낡은 문제가 되므로, **직전 새벽 3시** 이전에 시작한 미완료 세트는 폐기하고 새로 만든다.

- 자정이 아니라 새벽 3시인 이유: 리셋 순간에 학습이 끊기는 사용자를 줄이려고
  (밤 11시에 시작해 새벽 1시까지 푸는 세션은 안 끊긴다).
- 폐기는 `abandoned_at`만 찍으면 된다 — 조회 쿼리가 이미 걸러낸다.

> 이 장치가 없던 시절 버그: 7/21에 시작한 세트를 7/23에 이어받아, 이틀 전 기준으로 뽑힌
> 문제를 계속 풀었다. 당시엔 세트당 상자 상한까지 겹쳐 "정답인데 상자를 안 주는" 증상으로 드러났다.

### 쿨다운 — `SET_COOLDOWN = 30초`

직전 세트를 완료한 지 30초가 안 지났으면 `questions: []` + `cooldown_until`을 반환한다.

### 중단 — `abandon_quiz_set()`

활성 세트에 `abandoned_at`을 찍는다. 클라가 퀴즈를 중간에 나갈 때 호출.

## 5. 채점 — `grade_answer()`

전체가 `@transaction.atomic`.

### 검증 순서

1. **서명 검증** — 위조 토큰이면 `InvalidQuestionToken`.
2. **단발 토큰만 TTL 재검증**(300초). 세트 토큰은 `set_id` 생존으로 대신한다.
3. **중복 채점 방지**
   - 단발: `QuizLog.token_hash` 유일성으로 차단.
   - 세트: `QuizSetItem.answered` 플래그로 차단.
     (`signing.dumps`가 같은 payload에 같은 토큰을 만들어서 `token_hash` 검사는 오탐이 남)
4. **정답 판정** — `choice_index == payload['ci']`. 서버가 계산한다.

### 이후 순서

```
SRS 갱신 → Daily 조회(행 잠금) → 상자 지급 판단 → QuizLog 기록
        → Daily 저장 → 마일스톤 보너스 → QuizSet 갱신
```

### 응답

```json
{
  "is_correct": true,
  "srs": {"repetitions": 2, "interval_days": 10, "ease": 2.5, "due_at": "..."},
  "box_id": 17, "box_grade": "burgundy",
  "set_boxes_earned": 3, "set_completed": false,
  "milestone_bonus": 10, "today_correct_count": 20
}
```

## 6. SRS — 간격 반복

### 개념

한 번 맞힌 항목을 계속 보여주는 건 낭비고, 틀린 항목은 자주 봐야 한다.
그래서 **맞힐수록 다음 출제까지의 간격을 늘리고, 틀리면 되돌린다.**
"문제를 풀면 한동안 안 나오는" 동작이 이것이다.

### 상태 — `SrsState` (유저 × 항목 1행, 이력 아님)

| 필드 | 기본 | 뜻 |
|---|---|---|
| `ease` | 2.5 | 난이도 계수. 클수록 간격이 빨리 늘어남(최저 1.3) |
| `interval_days` | 1 | 현재 복습 간격(일) |
| `repetitions` | 0 | **연속** 정답 횟수(틀리면 0) |
| `due_at` | — | 다음 출제 예정 시각 |
| `last_result` | — | 최근 정답/오답 |

### 갱신 — `_apply_sm2()` (SM-2 간이판)

```python
SRS_FIRST_INTERVAL  = 3    # 1번째 정답
SRS_SECOND_INTERVAL = 10   # 2번째 정답
SRS_LAPSE_INTERVAL  = 3    # 오답
```

**정답**
- `repetitions == 0` → 3일
- `repetitions == 1` → 10일
- 그 이상 → `직전 간격 × ease` (반올림). ease 2.5면 10 → 25 → 63일…
- `repetitions += 1`

**오답**
- `repetitions = 0`, `interval_days = 3` → 3일 뒤 다시. 사다리를 처음부터 다시 오른다.

**항상**
- `ease` 갱신(정답=quality 5 유지 / 오답=quality 2 감소, 최저 1.3)
- `due_at = now + interval_days`

### 한계

- 간격 단위가 **일(day)** 뿐이라 최소 3일. **같은 세션에서 틀린 걸 다시 복습하는 흐름이 불가능**하다.
- 응답 품질이 정답/오답 2단계뿐(`answer_ms`는 기록만 하고 SRS에 안 쓴다).
  "겨우 맞힘"과 "쉽게 맞힘"을 구분하지 못한다.

## 7. 보상

### 캐시상자 — 정답 시

**상한은 일일 하나뿐**이다(`MAX_BOXES_PER_DAY`). 세트당 상한은 제거됐다 — 세트가 날짜를 넘겨
이어질 수 있어서, 오래된 세트를 재개하면 정답을 맞춰도 상자가 안 나오는 버그의 원인이었다.

```python
if daily.boxes_earned < MAX_BOXES_PER_DAY:
    box = CashBox.objects.create(
        user=user, grade=_roll_box_grade(), burst_count=_roll_burst_count(),
    )
```

**등급**(생성 시 확률로 결정) — 개봉 시 등급별 범위에서 캐시를 뽑는다.

| 등급 | 가중치 | 개봉 보상 범위 |
|---|---|---|
| `normal` | 30 | 1~4 |
| `purple` | 40 | 5~15 |
| `burgundy` | 30 | 16~40 |

**묶음 상자** — `BOX_BURST_CHANCE = 0.5` 확률로 `burst_count = 3`.
3이어도 **인벤토리·광고 횟수는 1개**로 세고 캐시만 개수만큼 각각 뽑는다.
`reward_cash`는 합계, `reward_breakdown`은 개별 목록, **원장은 합계 1건**.

> ⚠️ 위 수치는 전부 **임시 테스트값**이다. 배포 전 원복 대상은 §9 참조.

### 마일스톤 보너스 — 당일 정답 N개마다

상자와 무관하게 **캐시를 직접** 지급한다.

```python
QUIZ_MILESTONE_INTERVAL = 10   # 당일 정답 10개마다
QUIZ_MILESTONE_BONUS    = 10   # 10캐시
QUIZ_MILESTONE_MAX      = 20   # 하루 최대 여기까지(10, 20번째)
```

`daily.correct_count`가 10의 배수가 될 때 지급하고, 20을 넘으면 더 안 준다.
`Daily`는 매일 0으로 리셋되므로 자연히 하루 단위다.

## 8. 오프라인 — `sync_answers()`

잠금화면 등에서 네트워크 없이 푼 답안을 나중에 일괄 전송한다.

- **SRS·통계만 갱신하고 상자는 절대 주지 않는다.** 오프라인 답안은 시점·정합성을
  신뢰하기 어려워 캐시를 걸지 않는다.
- 각 항목의 결과는 `{'status': 'ok' | 'invalid' | 'already_graded'}`로 개별 반환.
- 중복은 `token_hash`로 차단.

### 클라 진행 커서 ⚠️

`store/quizSet.markAnswered()` — **답을 제출한 즉시** 커서를 올리고 캐시 문항을 `answered`로 찍는다.

> 이걸 '다음' 버튼에서만 하던 시절 버그: 답을 고르고 결과 화면에서 앱을 나갔다 오면
> 같은 문제가 다시 나왔고, 재제출하면 서버가 "이미 채점됨"으로 400을 줘서
> 정답/오답 표시 없이 다음으로 넘어갔다.

## 9. ⚠️ 배포 전 원복할 임시값

전부 테스트 편의로 올려둔 값이다. 그대로 배포하면 지급액이 크게 샌다.

| 상수 | 현재 | 비고 |
|---|---|---|
| `MAX_BOXES_PER_DAY` | **50** | 원래 정한 값 20 |
| `_BOX_GRADE_WEIGHTS` | 30/40/30 | 버건디·보라가 과하게 자주 나옴 |
| `BOX_BURST_CHANCE` | **0.5** | 기대 지급액이 2배가 됨 |
| `BOX_REWARD_RANGE` | (1,4)/(5,15)/(16,40) | 전체가 임시 |

## 10. 모델 관계

```
User ─┬─ SrsState   (user × item_type × item_id)  ← 현재 상태
      ├─ QuizLog    (푼 기록. 탈퇴 후 1년 보관)
      ├─ QuizSet ─── QuizSetItem (10개)
      ├─ Bookmark
      ├─ Daily      (하루 1건 집계)
      └─ CashBox    (정답 시 생성)

ItemType.WORD  → Word.id    (논리 참조, FK 아님)
ItemType.KANJI → Kanji.id
ItemType.KANA  → Kana.id
```

`item_id`는 **FK가 아니라 논리 참조**다. `item_type`에 따라 가리키는 테이블이 달라진다.
